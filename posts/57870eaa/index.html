61. 列表页文章少时，网站信息与侧栏卡下移全宽展开

效果

分类页、标签页或最后一页文章很少时，主列表只有两三张卡片，右侧却还挂着一整列侧栏，页面下半截会出现一块很大的空白。原来的第 53 节只把「网站信息」搬到主列底部，主列仍然只占 74% 宽，右边那一截还是空的。

这一节把「网站信息」也从主列请出来，和公告、欢迎来访、倒计时、那年今日一起排进 #content-inner 的整页全宽网格：

  • 桌面端（≥ 900px）先量主列表和侧栏的真实内容高度。
  • 网站信息放第一行，公告第二行，欢迎来访占 7/12、倒计时占 5/12，那年今日收尾；页面上缺哪张就跳过哪张。
  • 每搬一张重新量一次，侧栏高度回到主列表附近就停，不会一次全部搬空。
  • 新增文章把空间占掉后，下一次同步会先全部放回原位，再按新的剩余空间重新分配，所以只收回不需要的那几张。
  • 手机端不搬，网站信息和侧栏卡全部放回，保持整页纵向滚动。

本站 1440px 下实测：第 4 页（3 篇）展开网站信息、公告、欢迎与倒计时；4 ~ 6 篇只展开网站信息、欢迎与倒计时；8 篇只展开网站信息与欢迎；10 篇以上不再展开。这个数量不是写死的，由高度计算得出。

为什么不能直接 appendChild 了事

只在需要的时候移动卡片，必须解决三件事：

  1. 原位怎么记：卡片原来在 #aside-content 里，有的在 .sticky_layout 里，有的直接挂在侧栏下。只记父节点不够，还要记它在兄弟节点中的位置，否则恢复后顺序会乱。
  2. 高度怎么量：主列表和侧栏都是 flex 子项，侧栏会被拉伸到和主列表一样高。直接读 aside.offsetHeight 永远量不出「侧栏内容其实更矮」，要取它直接子元素的最底部。
  3. pjax 怎么活：pjax 只替换 #body-wrap，脚本本身还在。必须监听 pjax 完成事件重新同步，同时避免重复创建容器。
  4. 网站信息不在侧栏：第 53 节先把 .card-webinfo 搬进了 #recent-posts，它的位置由 list-webinfo.js 管。展开脚本要先找到这张卡，再和侧栏卡一起处理；只查 #aside-content 是找不到的。

本站的做法是：搬走之前在原位插一个注释节点 <!--hg-side-fill-slot--> 当占位，回来时插到注释前面，再把注释删掉。网站信息和侧栏卡都按这个办法记位置，注释不可见、不占布局，顺序却可以精确保留。

调参与边界

  • 什么时候不启用：窗口小于 900px、页面没有文章、找不到 #aside-content 或 #content-inner 时直接返回，不做任何移动。

改完怎么验证

  1. 生成：在博客根目录执行 ./node_modules/.bin/hexo generate，确认最后一行是 Generated。
  2. 短列表：找文章最少的一页（本站是第 4 页，3 篇），桌面宽度下检查：
    • 文章下方出现一条横跨主栏和侧栏的展开区；
    • 网站信息第一行铺满，统计项按四列排开；
    • 公告铺满一行，欢迎来访和倒计时按 7 / 5 并排；
    • 右栏保留作者卡或那年今日，没有被搬空；
    • 标题、公告入口和倒计时与卡片边缘之间保留内边距，没有贴边；
    • 页面没有横向滚动条。
  3. 动态回收：临时复制文章卡片，分别凑到 4、6、8、12 篇，每次调用一次 window.hgSideFillSync()。数量应逐级减少，12 篇时容器消失、全部卡片回到侧栏，顺序和原来一致。
  4. 手机端：把宽度缩到 390px，确认展开容器被移除、网站信息回到侧栏、所有卡片归位，页面可以整页向下滑，不出现内部滚动条。
  5. pjax：从首页点到第 4 页，再返回首页，确认 #hg-side-fill 只有一个，没有重复容器，也没有卡片丢失。
  6. 硬刷新：改过 CSS / JS 后按 Ctrl + F5；启用了 Service Worker 的话，到 DevTools → Application → Service Workers 点一次 Update。

62. 关于页：GitHub / Gitee 贡献度热力图

效果

关于页多一块「开源贡献度」：每个账号一张卡，53 周 × 7 天的热力图，鼠标停在格子上显示日期和当天贡献数，卡片顶部是「过去一年 N 次贡献」和日期范围；鼠标不需要精确对准也有 title 提示。手机端格子横向滑动，页面本身不出现横向滚动条。

配色不写死：五档颜色全部由当前主题色 --theme-color 按透明度混合出来，在「美化设置」里换主题色、切换暗色模式都会立即生效。

为什么不用现成插件

hexo-githubcalendar 是最常见的做法，但它有几个限制：只读站点配置、一次只能一个账号、色板写死、依赖 python-github-calendar-api.vercel.app。这个接口和 akilar 的备用接口现在都连不上，Gitee 也没有对应的贡献度接口。

所以这里换一种分工：数据在构建时抓，构建脚本输出 /github-calendar.json，页面只负责把 JSON 画成热力图。好处是不再依赖运行时接口，GitHub 和 Gitee 可以混在同一个列表里，新增账号只改配置。

数据源说明：

  • Gitee 没有公开的贡献度接口，这里抓个人主页：主页 HTML 里每个格子都带 data-content='N个贡献：YYYY-MM-DD'，服务端直接渲染，不需要登录。Gitee 改版改结构时会抓不到，此时回退缓存。

这里只放挂载点，不要直接写 <script>。kramed 遇到 <script> 行会进入 HTML 块，把后面的 ## 最近在折腾什么 一直到下一个 HTML 标签之间的内容全部当纯文本输出，页面上的 Markdown 会整段失效。脚本交给构建脚本里的 after_render:html 过滤器，紧跟着挂载 div 注入，data-pjax 保证 pjax 往返时随内容重新执行；渲染函数每次先清空 #hg-ghc 再画，不会叠出第二份。

为什么数据不直接写进页面

Hexo 的 db.json 会缓存页面的渲染结果：如果直接在页面的标签里输出贡献数据，源文件没变，页面就一直用旧内容，贡献度不会更新。所以这里让构建只产出 /github-calendar.json，页面保持静态、可以放心缓存，数据每次构建都是新的。

  • 展示形式的原插件是 hexo-github-calendar（Zfour），本站只借鉴它的样子，数据源和渲染都重写了。

调参与边界

  • 加账号：往 accounts 里加一项就行，platform 只认 github 和 gitee，写错按 github 处理。
  • 格子大小：改 .hg-ghc 的 --hg-ghc-cell-size 和 --hg-ghc-gap，月份标签的偏移是按构建时的 CELL + GAP 算好的，两边要一起改。
  • 颜色深浅：改 --hg-ghc-l1 ~ --hg-ghc-l4 的百分比；不想跟主题色，就把这四个变量换成固定颜色。
  • 等级阈值：构建脚本里 level() 按 1 ~ 2 / 3 ~ 5 / 6 ~ 9 / 10+ 分四档，提交量小的话可以把阈值调低。
  • 接口失效：GitHub 源可以换成任意返回 { contributions: [{ date, count }] } 的服务；Gitee 主页改版要同步改正则。
  • 缓存：.github-calendar-cache.json 在博客根目录，删掉会重新抓取；没有缓存又抓取失败时，页面显示「贡献度数据暂不可用」。

  3. 主题联动：美化设置里换主题色，格子颜色立即变化；切暗色模式，空格子变暗、有色格子保持。
  4. 手机：宽度缩到 390px，格子区域可以横向滑动，页面本身没有横向滚动条。
  5. pjax：首页 → 关于 → 首页 → 关于，#hg-ghc 里始终只有一份卡片。

63. SEO 四件套：RSS 订阅、站点地图、robots.txt、nofollow

效果

调参与边界

  • 订阅源体积：content: true 会带全文，limit 越大文件越大；只想给阅读器摘要就关掉 content。
  • 站点地图范围：两个插件默认收录 posts 和 pages，不含标签/分类分页；需要的话用插件的过滤参数排除指定文章。
  • robots 生效时间：改完部署后要等搜索引擎重新抓取，Google 可以用 Search Console 的 robots.txt 测试工具当场验证。
  • nofollow 范围：只影响渲染出来的文章正文；友链页如果是主题模板或数据文件生成的，要自己补 rel="nofollow"。
  • 域名变更：url 一旦改动，站点地图、feed 里的绝对链接会全部跟着变，换域名前先把旧链接做 301。

64. URL 持久化：abbrlink 短链 + 旧日期链接 301

为什么原来的「持久化」没生效

常见三种情况，本站当时是全中：

  1. 插件不在依赖里：hexo-abbrlink 装过、也把 abbrlink 字段写进了每一篇文章，但没写进 package.json，后来 npm install 或清理 node_modules 时被删掉，:abbrlink 没人提供值；
  2. permalink 没切：还停留在默认的 :year/:month/:day/:title/，所以输出始终在 public/2026/11/22/文章名/ 下；
  3. 改了没清缓存：改完 permalink 直接 hexo g，db.json 里旧路由缓存还在，输出看起来没变化。

判断方法：看 package.json 有没有 hexo-abbrlink、_config.yml 的 permalink 是否含 :abbrlink、public/ 下有没有 posts/ 目录，三项缺一不可。

第一步：装插件并切 permalink

文件：[Blogroot]/_config.yml ｜ 改法：修改 URL 段并追加 abbrlink 段。

两条容易踩的坑：

  • 不要加 force: true：加了每次构建都会按标题重算 abbrlink，等于把「持久化」又破坏了。文章里已有 abbrlink 时插件会原样保留。
  • 改完必须 hexo clean && hexo g，否则 db.json 的旧路由缓存会让输出保持不变。

生成后 public/posts/xxxx/ 就是文章新地址，sitemap.xml、atom.xml 里的链接会自动跟着变。

第二步：旧链接跳转页

老站被搜索引擎收录、外链、站内历史链接都还是 /2026/11/22/文章名/ 这种形式，直接切 permalink 会全部 404。GitHub Pages、Vercel 这类静态托管改不了 HTTP 状态码，只能用跳转页兜底。

文件：[Blogroot]/scripts/permalink-redirects.js ｜ 改法：新建，整段写入。

跳转页是 200 + 客户端跳转，对搜索引擎只能说「别收录旧页、看 canonical」，权重转移不如真正的 301。

第三步：主站 Nginx 打真 301

文件：[Blogroot]/tools/gen-permalink-301.js ｜ 改法：新建，整段写入；执行 node tools/gen-permalink-301.js。

生成的 tools/nginx-permalink-301.conf 里是成对的 location：带斜杠和不带斜杠各一条，共 78 条。打开宝塔 → 网站 → 设置 → 配置文件，把内容粘进 server { } 里，保存后重载 Nginx。这样主站的旧链接返回的是真 301，备用站继续用跳转页。

调参与边界

  • 新文章：hexo new 时插件会自动生成 abbrlink 并写进 front-matter，之后改标题也不影响 URL。
  • 想换短链算法：alg 改 crc16、rep 改 dec 只影响之后新生成的值；已有值不会被覆盖。真要全部重算，才加 force: true，代价是所有旧链接失效。
  • 站内硬链接：历史文章里写死的 /2026/11/22/xxx/ 仍然会先命中跳转，建议逐步改成 /posts/abbrlink/；改的时候注意同步 tools/gen-permalink-301.js 的规则来源（只依赖 front-matter，不受影响）。
  • 隐藏文章：hexo-hide-posts 不影响跳转页生成，它们仍然会被生成，只是不出现在列表里。
  • 百度收录：百度对 301 的响应比较慢，改完在搜索资源平台提交新 sitemap，旧链接保留一段时间再观察。

改完怎么验证

  1. hexo clean && hexo g，确认 public/posts/ 下有 39 个目录，每个里都有 index.html。
  2. 打开任意 public/2026/11/22/hexo-magic5/index.html，应看到「页面已迁移」和指向 /posts/32894573/ 的跳转。
  3. 浏览器访问旧地址，应自动跳到新地址；地址栏只闪一下。
  4. curl -I https://cookiesky.cn/2026/11/22/hexo-magic5/，Nginx 规则生效时应返回 301；备用站返回 200 跳转页也属于正常。
  5. 检查 /sitemap.xml、/atom.xml 里已经是 /posts/.../ 新链接。
